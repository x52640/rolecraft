# 經歷資料與事實項

> 內容搬自已定稿的 `docs/spec-discussions/rolecraft-v01/spec.md`（2026-10-10，Codex 定稿確認 no_blockers）。
> F 開頭是原始功能描述，R 開頭是討論補充規則；**兩者衝突時以 R 為準**。D 編號見 `plan.md` 決策記錄。
> 權威範圍：Claim、四態、確認動作、匯出前檢查、來源變更失效。

## F04 個人經歷資料庫

每個專案整理為：名稱、問題／目的、使用對象、技術架構、功能、完成狀態、個人角色、實際成果、可公開連結、原始資料位置及確認狀態。

- 明確區分「計畫中」「文件標示完成」「使用者確認完成」「未知」。
- task 勾選只是文件證據，不等於已驗證上線或有成效。
- 個人貢獻、成果數字、使用人數等缺少依據時，向使用者詢問或留白。
- 保存履歷、文件及摘要的關聯；使用者可編輯、刪除及更新素材。
- 後續只更新新增或變更文件，避免每個職缺重新分析全部資料。

## R1 事實項與四態（C1）

- 經歷資料的最小單位是「事實項」：一個功能、交付物、個人角色、成果數字、使用人數、公開連結各是一項。專案摘要只是事實項的彙整，本身不帶確認狀態。
- 功能與交付物有完成狀態：計畫中／文件標示完成／使用者確認完成／未知（D4）。每個事實項都有依據：來源片段（SourceDocument 版本＋位置＋原文）及／或使用者確認（時間＋確認當下的文字）。沒有依據的一律視為未知。
- 三種使用者動作意義不同：
  - **接受修改稿**：只接受措辭，不確認其中任何事實項。
  - **確認事實項**：在事實項上逐項確認，記錄時間與當下文字。
  - **逐段確認**：使用者對某一段明確表示「本段內容屬實」，記錄時間與該段全文；用於使用者自己寫的或改過的段落。
- 生成稿的每一段都要列出所引用的事實項，以及該段把每一項寫成什麼完成程度（已完成／進行中／規劃中）。匯出前自動檢查：
  1. 引用的事實項存在。
  2. 寫成已完成的事實項必須是「使用者確認完成」（D14）；計畫中、未知、待複核、來源矛盾一律不得寫成已完成。
  3. 文字中的數字（百分比、人數、金額、年份）出現在引用的事實項、個人資料欄位或使用者確認過的文字中。
- 檢查 2 不通過的段落，只能改寫、刪除，或到事實項上確認，不能用逐段確認繞過；檢查 1、3 不通過或沒有任何引用的段落，可以改寫、刪除或逐段確認。處理完之前不能匯出。
- 〔第 2 輪補〕生成段落的引用在編輯時保留：使用者可以增加引用，不能只移除引用；要去掉引用只能刪除整段。所以仍帶引用的段落一律受檢查 2 約束；能靠逐段確認匯出的無引用段落，只有使用者自己新寫的段落，以及生成時就沒有任何引用的段落。
- 措辭與宣稱的完成程度是否相符無法自動判定，由使用者在 F07 的逐段對照中把關。
- 公司、職稱、任職日期由個人資料欄位帶入模板，不交給模型生成。
- 〔P1-T072〕客製履歷以工作經歷為主體：每段 Profile 經歷都要有一段經歷段落（段落歸屬＝該經歷），以已確認的經歷描述為原文、依職缺挑重點改寫；專案段落是補充，不能取代經歷；與職缺無關的經歷可精簡但不省略。
  - 經歷描述是使用者確認過的文字：經歷段落可以不引用事實項；生成端檢查時，數字、網址、倍數詞可來自所引用的事實項或**同一段**經歷描述（不認其他經歷）。不引用事實項的經歷段落照上面規則屬「生成時就沒有任何引用的段落」，匯出前要逐段確認。
  - 生成結果缺少某段經歷（模型沒產出，或產出的經歷段落沒通過檢查）時，由程式補一段「沿用原文」段落：文字＝該經歷描述、沒有引用、待接受，不額外呼叫模型。描述空白的經歷不補。沒有任何模型段落通過檢查時整份仍判失敗，不只靠補段產生版本。

## R2 來源變更與確認失效（C2）

- 事實項的來源片段綁定 SourceDocument 的內容版本與片段原文。
- 〔第 2 輪改〕增量更新時，看引用片段**所在的區塊**（以標題或空行分隔的段落）：區塊完全沒變 → 保留原狀態；區塊有任何變更或片段消失 → 事實項改為「待複核」，處理前不得用於新的生成。已經使用者確認的也一樣，因為新內容可能和確認相矛盾。字串仍在不代表依據仍有效（例如同一段加上「先前記載有誤」）。
- 來源檔被刪除或撤銷授權：只靠該來源的事實項不得再用於新的生成；已經使用者確認的可以保留，依據只剩使用者確認，畫面標示「來源已移除」。
- 〔擁有者裁定 #15〕撤銷後重新授權、內容未變 → 恢復撤銷前狀態，不呼叫模型：
  - 事實項因撤銷授權變成「來源已移除」的當下，保存撤銷前的複核狀態，以及每份來源文件當時的內容指紋（hash）和事實項當時的內容（文字、完成狀態）。只有「所有來源都是撤銷授權、片段綁的正是當時版本、沒有使用者確認」的事實項才保存；來源被刪除、待確認或另有其他問題的不保存。
  - 之後每份來源都重新授權、目前內容指紋都和保存值相同、片段所在區塊照常判定為沒變、事實項內容也和保存時相同 → 恢復成保存的狀態並清掉保存值；這只是重新判定，不重新分析該文件、不呼叫模型。
  - 有任何一份來源仍未授權 → 維持「來源已移除」，保存值保留，等其他來源也重新授權。
  - 不恢復並清掉保存值（之後照本節其他規則處理）：撤銷期間任何一份來源內容指紋變了、來源被刪除或變成待確認、片段判定有變、事實項另有其他來源問題、事實項內容被改過、事實項已被使用者確認（已確認的依據是使用者確認，維持標示不受影響）、狀態已不是「來源已移除」。
  - 舊資料（沒有保存值的「來源已移除」事實項）一律不恢復。
- 〔第 2 輪改〕文件其他部分有變更時，重新分析該文件。分析發現來源互相矛盾（兩份文件之間，或同一文件內的更正、撤回，例如一處寫完成、另一處寫計畫中或已撤下），事實項標示「來源矛盾」，按未知處理，直到使用者確認。
- 已匯出的版本保存當時引用片段的副本（R3），不受來源後續變更影響。

## 專案分組與事實項歸屬（D23，P1-T063）

- 專案（ProjectEvidence）只由使用者確認建立：AI 依文件摘要提出分組建議，建議本身不建立任何專案；使用者在確認前可改名、取消某組、把文件移到別組或移出（留在未分組）。只由使用者在專案頁按「建議專案分組」觸發，不自動執行。
- 建議的輸入只有「目前已授權、最近一次列舉仍在、尚未屬於任何專案、有摘要」的文件：全域摘要中該文件的一段（`document_summaries`）與文件在授權資料夾內的相對名稱；不送絕對路徑、不送原文（R4）。摘要與名稱是資料不是指令（D6），提示照分析提示的資料區塊隔離；文件在提示中只用本機編號（D1、D2…），模型只能引用編號。
- 建議輸出驗證：整份須是規定格式的單一 JSON 物件；引用未知編號、同一文件出現兩次、多餘欄位、組名空白或過長、空組、一組超過建立上限（1,000 份文件，與 `claims.create_projects` 相同；不自動拆組）→ 整份不採用（不部分採用）。沒被分到任何組的文件留在「未分組」。不自動重試，使用者可再按一次。
- 文件歸屬：每份文件至多屬一個專案（storage `project_documents`，來源文件 ID 為主鍵；ProjectEvidence schema 不變）。確認建立時每份文件須是目前已授權、最近一次同步仍可讀（仍有摘要）、尚未屬於任何專案的來源文件，且同一請求內不重複；任一不符整批不建立。分析同步時發現文件已刪除或讀不到（符號連結、過大、二進位等，視同刪除），同一交易清掉該文件的摘要與已分析版本，所以它不再進建議、不能被建成專案；恢復可讀時重新分析。
- 事實項歸屬規則（建立專案與重新分析共用）：事實項所有來源片段的文件都屬同一專案 → 歸入該專案；來源跨多個專案、有任一來源文件不屬任何專案、或沒有來源片段 → 留在未歸專案。
  - 建立專案時只對「目前未歸專案」且依規則歸到「這次新建的專案」的事實項套用：已歸入其他專案的不搬動，使用者移回未歸專案的也不會因為建立別的專案被拉走（只要它的文件不在新專案）。
  - 重新分析（`commitUnit`）時只對該單元新產生的事實項套用，與事實項同一交易寫入（失敗整筆回滾）；既有事實項（含使用者手動搬過的）不搬動。
- 整理操作：改名；合併（來源專案的事實項與文件併入目標專案，來源專案刪除）；把事實項移到另一專案或移回未歸專案（一個事實項至多在一個專案）；刪除專案（事實項回到未歸專案、其文件不再屬任何專案，事實項本身不刪）。專案摘要維持空字串（D23：不由 AI 填寫）。
