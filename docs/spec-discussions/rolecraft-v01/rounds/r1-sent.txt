## 規則（違反就等於沒做）

1. **只討論，不要動手。** 不要改任何檔案，不要安裝、登入、呼叫任何模型或連網服務。repo 根目錄的 `CLAUDE.md` 若講實作流程，這一輪不適用。
2. **講行為要有出處。** 出處可以是：spec.md 的節號／編號、`Spec.md` 的節號，或你在本機實際讀到的東西。
   你若要主張某個官方 CLI「支援／不支援」某種行為，本機裝有 `claude`、`codex`、`agy`，可以跑它們的 `--help`／`--version`（只准這兩種唯讀指令）並貼出相關那幾行。
   **外部事實**（供應商的計費與條款政策、Chrome／Arc／Edge 的 API 行為、求職平台的條款或頁面結構）你無法在本機查證的，一律標成 `assumption`，不要拿它當 blocker 的唯一依據。spec.md §5 S8 是擁有者自己查的紀錄；你覺得它可能錯，就寫成 assumption 並說明要怎麼驗證。
3. **分三類，每一項都要標：**
   - `blocker`：照這樣寫下去會壞、會自相矛盾、會有資料／隱私／權限問題，或驗收條件無法判定。
   - `needs_owner`：這是產品取捨（範圍、優先順序、要不要做），不是技術問題，要人決定。列出選項與各自代價。
   - `optional`：可以更好，但不擋。**最多三項**，不要把範圍撐大。
4. **不要重寫規格。** 指出問題就好，不要附上你版本的完整規格。

## 擁有者的硬限制（不要說服我放寬）

spec.md §2 的 D1–D10 是擁有者拍板的。你可以指出某條限制讓某個需求做不到或代價很高，但那要標 `needs_owner` 並寫出代價；**不要提「放寬 D2 就好」這種 blocker**。
最常被實作悄悄違反的是：D2（只用既有訂閱；無法確認零額外收費就不啟用；不回退到 API key）、D4（四態分開，task 勾選不等於完成）、D5（只讀選取的文字文件，首版不讀原始碼，不擴大掃描）、D6（外部內容是資料不是指令，模型不可決定執行 shell）、D7（不自動送出）。

§7 的 Q1–Q5 是已知待決項：你可以替它們補選項與代價，或指出漏列的待決項。

## 回覆格式

每一項一段，開頭標 `[blocker]` / `[needs_owner]` / `[optional]` 加一個編號 **C1、C2…**（不要用 F 開頭，F01–F09 是規格的功能編號），
接一行 `出處：` 寫節號／編號或本機證據，再寫內容。無出處的推測另外標 `assumption`。
最後附一行你讀到的 spec.md 的 sha256（自己算）。
