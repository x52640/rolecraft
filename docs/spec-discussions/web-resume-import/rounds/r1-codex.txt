[blocker] **W1：「可見內容精簡成區塊」沒有唯一可判定的結果。**
出處：`docs/spec-discussions/web-resume-import/spec.md` §5.1、§8（54、109 行）。
「可見」沒有界定是目前視窗內，還是整份已載入且未隱藏的內容；也沒有履歷本文範圍、巢狀元素去重、表格閱讀順序、表單值如何轉成文字的規則。例如合成 DOM `<li><p>完成付款系統</p></li>`，輸出一個區塊或兩個都符合目前文字。「標籤＋值」也沒有說明標籤是否包含在來源文字中。這直接影響截斷、個資移除及完整區塊照抄檢查；只要求「有 fixture、有測試」無法判定哪個結果才正確。

[blocker] **W2：新操作不能直接套用現行發送者驗證。**
出處：規格 §5.1（55 行）；`apps/extension/src/relay/sender.ts:46–53`；`apps/extension/src/sites/registry.ts:35–49`；`docs/specs/bridge.md`「操作」（25 行）。
現行驗證要求發送頁是職缺頁，而且所有 content script 擷取都必須有 `captureMethod === 'auto'`；新 payload 沒有這個欄位，直接沿用會被拒。若只把履歷網址加入共用 registry，又會讓職缺／訊息操作取得履歷頁的授權。需要按「操作×頁型」界定授權。另外現行程式只檢查 `sender.url` 與平台，沒有比對 `payload.url`；規格應明確區分發送頁驗證、來源 URL 驗證及兩者一致性，§8 目前也沒有涵蓋操作與頁型錯配。

[blocker] **W3：字數上限沒有守住橋接大小，而且截斷標記無處傳遞。**
出處：規格 §5.1–§5.2（54–62 行）；`apps/helper/src/bridge/framing.ts:6–13,42–48,80–88`；`apps/helper/src/bridge/host.ts:68–77,138–148`；`docs/specs/bridge.md`「信封與請求 id」（116 行）。
repo 自訂的請求上限與回應上限都是 **1 MiB**；超大請求會造成協定斷線，超大回應改回 `internal_error`。區塊數與字數不能直接保證 UTF-8 JSON 加信封的位元組數合格，也沒有涵蓋原文、草稿重複出現在回應的大小。更直接的矛盾是：54 行要求「截斷並標示」，55 行 payload 卻只有 `{platform,url,capturedAt,blocks[]}`，沒有完整性狀態；helper／編輯器無法區分完整來源與截斷來源。

[blocker] **W4：「同一種資料流」目前沒有容納區塊來源的契約。**
出處：規格 §5.2–§5.3；`packages/contracts/src/bridge/editor/import.ts:24–28,67–79,112–119`；`apps/helper/src/handlers/import/ai-runner.ts:28–31`；`packages/pipeline/src/resume-parse/output.ts:23,44–52`；`apps/editor/src/pages/import/ParsePreview.tsx:12–13,45–53`。
現行結果、AI 草稿、AI 輸入與預覽都使用頁碼／行號；模型輸出的來源編號甚至只接受 `頁-行` 格式，`b12` 會使整份輸出不合格。Q3 選新增查詢或擴充 `import.get`，都不能單獨解決這些契約。規格尚未界定網頁來源如何貫穿原文預覽、欄位出處、AI 狀態與校正流程；把區塊偽裝成 PDF 行則會丟失種類／層級，並產生假的出處。

[needs_owner] **W5：擷取內容活多久，不能引用不存在的「PDF 暫存期限」。**
出處：規格 §5.2（62 行）；`apps/helper/src/handlers/import/import-service.ts:3,38–51,63–86,117–126`。
PDF 原始 bytes 解析後不保留；結果、校正與 AI 來源留在記憶體，預設最多 20 筆、超量淘汰最舊，確認後也沒有立即清除，更沒有時間型 TTL。選項 A：網頁完全沿用這個生命週期，代價是 helper 重開後原文與工作階段消失。選項 B：落在資料區並訂期限，代價是新增持久儲存、清除與重啟恢復規則，也延長未遮罩個資的留存。兩者不能同時稱為「與 PDF 暫存一致」。

[blocker] **W6：現有去個資規則依賴 PDF 額外提供的姓名線索。**

[blocker] **W7：個資遮罩後會還原，後續生成又可能送出去。**
出處：規格 D7、§5.3；`packages/pipeline/src/resume-parse/check.ts:58–76`；`apps/editor/src/pages/import/ai-form.ts:56–63`；`packages/pipeline/src/generation/prompt.ts:139–150`；`packages/pipeline/src/intro/prompt.ts:89–102`。

[blocker] **W8：`match.ts` 的「行」規則不能直接替換成「區塊」。**
出處：規格 §5.3（68 行）；`packages/pipeline/src/resume-parse/match.ts:36–51,62–75,99–109`；`packages/pipeline/src/resume-parse/check.ts:62–72`。
有兩個可由程式推導的反例。第一，完整區塊文字若是「負責開發\n維護系統」，模型原封不動回傳，`coversWholeLines` 卻會把回傳值拆成兩段、把來源區塊視為一段，因而拒絕。第二，年月與「至今」分別是兩個區塊：只引用「至今」缺年份；一起引用年月又無法滿足「值必須用到每個引用來源」。兩者都會拒絕真實原文。需要界定區塊內換行與日期上下文如何處理，不能只寫「沿用」。

[blocker] **W9：第二次匯入若沿用現行確認流程，會讓生成與匯出失效。**
出處：規格 §5.2；`apps/helper/src/handlers/import/import-service.ts:99,117–124`；`apps/helper/src/handlers/resume/generation.ts:126–131`；`apps/helper/src/handlers/export/export-create.ts:68–75`。
每個新工作階段的 `profileId` 都從 null 開始，第一次確認便建立新的 Profile；只有同一工作階段重複確認才覆寫原 ID。但生成與匯出都要求資料庫恰好只有一份 Profile。因此沿用流程確認兩次獨立網頁擷取，會得到兩份 Profile，後續被拒。規格需要交代「新擷取」如何更新既有單一使用者資料，而不是把擷取工作階段等同於新 Profile。

[blocker] **W10：照片的內部檔案參照與橋接輸入沒有分界。**
