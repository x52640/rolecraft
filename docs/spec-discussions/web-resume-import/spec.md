# 從求職網站履歷頁匯入、PDF 只負責輸出

> 這份是這場討論的**唯一規格**。Codex 唯讀，只有協調者寫這份檔。
> 引用程式碼一律寫「檔名＋識別字」，不寫行號、不用 markdown 連結。
> 〔第 1 輪補／改〕、〔第 2 輪補／改〕標記各輪後的改動：W 編號是 Codex 的意見（`rounds/r1-codex.txt`、`rounds/r2-codex.txt`），N 編號是協調者自己加的。〔擁有者 2026-10-12 裁決〕標記第一次定稿確認後擁有者的裁決（§7 的 Q 與新的觸發方式 D9），〔裁決後補〕是協調者為了落實裁決補的細節。逐項理由見 `decisions.md`。

## 1. 要解決什麼問題

使用者的履歷本來就放在求職網站（104、Cake、Yourator…），也會登入網站編輯。現行匯入要使用者先下載 PDF，再由本機從 PDF 文字層反推版面；2026-10-12 實測 104 PDF 修了多輪（跨頁誤判、部首相似字、日期歸段），而把 PDF 純文字交給 AI 整理時，因為丟失了字級與位置，AI 會把「職務類別」誤當職稱、漏掉描述。網頁 HTML 本身帶有標題、清單、「標籤：值」等結構，同一套「讀已開啟頁面 → AI 整理」可以套用到多個網站，不必每站寫一套解析器。

另外，產品輸出端缺少照片：台灣履歷通常附照片，現行匯出 PDF 沒有照片欄位。

## 3. 限制

- **條款未查**：104／Cake／Yourator 是否允許個人擴充功能讀取「使用者自己的履歷頁」尚未查證（P1-T017 範圍已加入；docs/specs/open-verifications.md 也列為待查）。〔擁有者 2026-10-12 裁決，Q1〕條款明文禁止的網站不開放此功能（該站只剩手動輸入；PDF 入口照 5.5）；查不到明文 → 擁有者自負風險照樣開放（理由：自用、按下才讀、只讀自己的頁）。
- **擴充功能權限**：manifest 只有 `activeTab`、`scripting`、`nativeMessaging`，沒有 host_permissions、沒有宣告式 content_scripts（`apps/extension/src/manifest.ts` 的 `PERMISSIONS`）。要維持「使用者按下才注入、只讀當前分頁」的最小權限。〔擁有者 2026-10-12 裁決，D9〕點工具列圖示和按快捷鍵一樣會讓 Chrome 授予 activeTab（暫時取得目前分頁的網址與注入權；離開該網站或關掉分頁就收回）。現行點圖示本來就會授予，只是沒拿來注入，所以改成點圖示擷取不需要任何新權限，授權範圍也不變。
- **頁面內容是資料不是指令**（bridge.md R7）；content script 只能呼叫白名單操作（contracts `bridge/operations.ts` 的 `CONTENT_SCRIPT_OPERATIONS`，目前只有 `submit_job_capture`、`submit_message_capture`），service worker 會驗發送者框架、網址與平台（`apps/extension/src/relay/handler.ts` 的 `handleRelay`、`relay/sender.ts` 的 `authorizeSender`）。
- **不取 cookie、不代登入、不在背景開頁**；只讀使用者自己開著的那一頁。
- **計費**：只走使用者已選定的訂閱模型（providers R5、R6）；未選模型或不可用時不呼叫。
- **單檔 300 行、套件相依方向**（docs/specs/architecture.md），lint 會擋。
- **既有 Profile 形狀**：`packages/contracts/src/entities/profile.ts` 的 `Profile`（personalInfo 是「標籤→值」、experiences、skills、pdfParseConfirmed）；匯出由已確認的 Profile 帶入公司、職稱、日期（R1）。
- 〔第 1 輪補，W3〕**橋接單則上限**：瀏覽器→helper 自訂 1 MiB（helper `bridge/framing.ts` 的 `MAX_INCOMING_BYTES`，超過是協定錯誤、整條連線斷掉）；helper→瀏覽器 1 MiB（`MAX_OUTGOING_BYTES`，超過改回 `internal_error`）。
- 〔第 1 輪補，W9〕**只能有一份 Profile**：履歷生成、自介、匯出都要求資料區恰好一份已確認的 Profile（helper `resume/generation.ts` 的 `loadInputs`、`intro/intro-service.ts` 的 `profile`、`export/export-create.ts` 的 `confirmedProfile`），多一份就全部拒絕。

## 4. 現在的程式長什麼樣

- **擴充功能擷取骨架已有、但沒有任何站真的在讀內容**：
  - 快捷鍵 `capture-page` → `apps/extension/src/background/actions.ts` 的 `triggerCapture`：用 `sites/registry.ts` 的 `findSiteForUrl` 比對網址，符合才 `chrome.scripting.executeScript` 注入 `sites/<platform>.js`（只注入主框架）。
  - `SITE_REGISTRY` 只有 104 職缺頁（host `www.104.com.tw`、路徑 `/job/`）。
  - `sites/104/adapter.ts` 的 `adapter104.capture` 目前回 null（佔位），頁面只顯示「尚未支援」提示（`sites/104/notice.ts` 的 `showCaptureNotice`）。
  - 抽象：`sites/types.ts` 的 `SiteAdapter{platform, capture(doc, pageUrl)}`，回 `SubmitJobCaptureRequest`；`sites/runtime.ts` 的 `runSiteCapture` 經 service worker 轉給 helper。
  - 〔第 1 輪補〕工具列按鈕直接開編輯器（`background/main.ts` 的 `chrome.action.onClicked`，不看目前分頁）；擷取只有快捷鍵。〔裁決後補〕編輯器預設頁就是匯入頁（editor `app/routes.ts` 的 `DEFAULT_ROUTE_PATH`）。圖示提示文字是「開啟 RoleCraft 編輯器」、快捷鍵說明是「擷取目前的職缺頁」（`manifest.ts` 的 `buildManifest`）。快捷鍵在不支援的頁面只在圖示上提示（`main.ts` 的 `showTabNotice`：徽章＋該分頁的提示文字）；content script 的結果提示畫在頁面右上角（`showCaptureNotice`，shadow DOM、純文字），成功時不提示。`manifest.test.ts` 鎖住三個權限、沒有 host 權限、工具列沒有 popup。
  - 〔第 1 輪補，W2〕`authorizeSender` 對 content script 只檢查：主框架、`findSiteForUrl`（職缺頁規則）通過、平台相符、`captureMethod === 'auto'`；不比對 payload 裡的網址。
- **履歷匯入（PDF）**：`packages/resume-import`（`extract.ts` 的 `extractResumePdf`、`draft/layout104/build-104.ts` 的 `build104`、`draft/header-name.ts`）；AI 整理在 `packages/pipeline/src/resume-parse/`（`prepare.ts` 的 `prepareResumeParse`、`personal.ts` 的 `extractPersonal`、`redact.ts` 的 `createRedactor`、`check.ts` 的 `checkResumeParse`、`match.ts`、`run.ts` 的 `runResumeParse`）。AI 輸入目前是「頁-行」編號的純文字行。
  - 〔第 1 輪補，W4〕欄位出處、AI 草稿與模型輸出的來源編號都是頁碼／行號（contracts `ImportDraftField`、pipeline `output.ts` 的 `LINE_ID`、編輯器 `ParsePreview.tsx`）。
  - 〔第 1 輪補，W6〕本機姓名線索來自 PDF 專屬來源（helper `ai-source.ts` 的 `aiSourceOf`：104 規則、「姓名：」、頁首大字與英文別名）；`extractPersonal` 本身不知道哪個標題是姓名。
- **helper 匯入操作**（`apps/helper/src/handlers/import/`）：`import.pick_pdf`、`import.get`、`import.save_corrections`、`import.confirm`、`import.ai_parse`、`import.ai_status`；AI 背景執行在 `ai-runner.ts` 的 `createAiParser`（狀態只在記憶體），輸入由 `ai-source.ts` 的 `aiSourceOf` 組成。
  - 〔第 1 輪補，W5／W9〕匯入工作階段只在 helper 記憶體（`import-service.ts` 的 `createResumeImportService`：最多 20 筆、超過丟最舊，沒有時間期限；原始 PDF 解析完就丟）。每個工作階段第一次 `import.confirm` 會新增一份 Profile（`entry.profileId ?? newId()`），而且整筆取代寫入（storage `json-table.ts` 的 `upsert`）。
- **編輯器匯入頁**：`apps/editor/src/pages/import/ImportPage.tsx`、`useAiParse.ts`（每次有自己的操作 token、輪詢；`auto` 為 true 時換一筆匯入就自動開始整理，現行 PDF 是 104 版面按鈕、其他格式自動）。
  - 〔第 1 輪補，W14〕手動輸入只出現在選過 PDF 之後的核對畫面；編輯器沒有獨立的個人資料頁，也沒有讀取 Profile 的橋接操作。
- **PDF 匯出**：`packages/pdf-export` 的 `model.ts` `ResumeDocument{name, headline?, contacts, sections}`，沒有照片欄位；`template/html.ts` 的 `buildHtml` CSP 已允許 `img-src data:`；以使用者已安裝的 Chrome（puppeteer-core）繪製。helper `handlers/export/`（`export-create.ts`）由 Profile＋ResumeVersion 組文件。
  - 〔第 1 輪補，W12〕檔案儲存區以內容雜湊定址；helper 啟動清掃把不被任何匯出版本引用的檔當孤兒刪除（storage `export/pdf-cleanup.ts` 的 `sweepOrphanPdfs`）。「素材」＝匯出版本保存了副本的原件，刪除時套 D19（storage `application/materials.ts` 的 `MaterialKind`）。
- **寫回網站**：完全沒有；`bridge/operations.ts` 檔頭與 bridge.md R7 明寫刻意不提供。

## 5. 規格

### 5.1 擷取（擴充功能）

- **頁型**：每個支援的網站在 registry 另外登記「履歷頁」：網址規則＋履歷本文根節點的選擇器（〔第 1 輪補，W1、N3〕只讀根節點內，不讀頁首、側欄、推薦職缺、站內訊息等；找不到根節點＝擷取失敗、不送）＋〔第 2 輪補，W6〕選填的姓名元素選擇器（用途見 5.3）。實際規則待各站 DOM 樣本確定（Q2）。〔裁決後補〕網址規則要窄到只符合要讀的那一種頁：符合的頁面點圖示就是擷取、不再開編輯器。同一站的職缺頁規則與履歷頁規則不得重疊（registry 測試擋），所以任何網址最多屬於一種頁型。
- 〔擁有者 2026-10-12 裁決，D9；推翻第 1 輪 N2〕**觸發**（只有這兩種，都是使用者按下才發生）：
  - **點工具列圖示**：目前分頁網址符合某站的履歷頁規則 → 注入該站的履歷頁擷取腳本（只注入主框架）；其他頁面（含職缺頁、不支援的網站；拿不到分頁或網址時也一樣）照舊開編輯器、不注入。職缺擷取仍只用快捷鍵。
  - **快捷鍵 `capture-page`**：照舊可用，依網址決定職缺頁或履歷頁，注入對應的擷取腳本；都不符時沿用現行圖示提示（文字改成「不是支援的職缺頁或履歷頁」），不注入。
  - 〔裁決後補〕職缺頁、履歷頁的擷取腳本分開兩支，由 service worker 依網址選（打包方式比照現行 `sites/<platform>.js`），頁面裡不再判斷一次頁型；發送者驗證照下面「操作×頁型」的規則。
  - **權限**：不加任何權限（§3）。`chrome.action.onClicked` 收到的分頁物件在 activeTab 授權下帶網址，在處理函式裡用現有的 `scripting` 注入即可。manifest 仍只有三個權限，不加 host 權限、`tabs`、`contextMenus`，工具列也不改成 popup（現行 manifest 測試照舊通過）。
  - 〔裁決後補〕**說明文字**：圖示提示文字、擴充功能說明、快捷鍵說明改成講清楚兩種行為（例如圖示：「RoleCraft：在支援的履歷頁點一下擷取，其他頁面開啟編輯器」）。不做依頁面變換的圖示或提示文字（要另外加 `tabs` 或 `declarativeContent` 權限）。
  - 〔裁決後補〕**履歷擷取的結果**（由圖示或快捷鍵觸發都一樣；職缺擷取照現行）：
    - 擷取成功（helper 回成功，含標了截斷的）：service worker 開一個編輯器分頁（預設頁就是匯入頁），匯入頁顯示 `import.latest_capture`，也就是剛送達的這份；仍要使用者按「使用這份」才進入核對（5.2），也不會呼叫模型（5.3）。編輯器一律由 service worker 直接開、不經 helper（bridge.md 現行規則）。
    - 找不到本文根節點：不送任何東西、不開編輯器；頁面右上角顯示提示（沿用現行頁面內提示：shadow DOM、純文字）：「RoleCraft：這一頁找不到履歷內容（可能不是支援的履歷檢視頁，或網站改版了），沒有擷取或送出任何內容。可以到 RoleCraft 編輯器改用「手動輸入」（在其他分頁點 RoleCraft 圖示開啟）。」
    - 送出後失敗（helper 連不上、請求被拒或不符 schema）：不開編輯器；頁面顯示現行的擷取失敗提示，改成指向「手動輸入」。
    - 注入失敗（例如頁面還沒載入完、瀏覽器不允許注入）：不開編輯器，用現行 `showTabNotice` 的徽章與提示文字在圖示上提示（現行快捷鍵遇到注入失敗只寫主控台紀錄，這裡一併改）。
  - **代價**：在履歷頁上點圖示不再開編輯器；擷取失敗時要到其他分頁點圖示才能開編輯器。每點一次就是一次新的擷取（記憶體最多 20 筆、超過丟最舊，5.2），成功就多開一個編輯器分頁。
- 〔第 1 輪改，W1〕**區塊抽取規則**（依 DOM 順序；同一份 fixture 只能有一種正確輸出）：
  1. 只讀主框架、根節點內。不讀不渲染的元素（display:none、visibility:hidden、`hidden` 屬性、`aria-hidden="true"`）與 script、style、noscript、template、svg、圖片（含 alt）；不限於目前捲動到的範圍。收合未展開的內容讀不到，各站樣本要記錄這件事。
  2. 區塊單位：h1–h6 → 標題（層級＝數字）；li → 清單項（層級＝巢狀深度，〔第 2 輪改，N5〕超過 6 層一律記 6）；tr → 表格列（儲存格以 Tab 連接）；dt＋dd、只有 th＋td 兩格的列、label＋表單控制項 → 標籤＋值（標籤另存，不算區塊文字）；其他文字以最近的區塊層級祖先為一個段落。每段文字只屬於最近的一個區塊；巢狀的清單、表格各自成區塊，不重複計入外層。
  3. 文字取渲染後的文字，連續空白合併成一格；元素內的換行（br 或區塊內換行）切成連續的多個區塊，種類、層級、標籤相同——每個區塊只有一行（W8）。〔第 2 輪補，W18〕同一元素切出的第二個以後的區塊標 `continues: true`（接續上一個區塊）。
  4. 表單控制項：密碼、隱藏、檔案欄位不讀；其他只讀目前值（select 取選中項的文字）。
  5. 不送原始 HTML、元素屬性、連結網址。
  6. 〔第 2 輪補，N6〕「可見」與「渲染後的文字、換行」以 Chrome 實際渲染為準（例如 `checkVisibility`、`innerText`）。jsdom 沒有這兩者，所以抽取邏輯把「是否可見、文字與換行」做成可注入的判定：合成 DOM 測試注入簡化判定；各站 fixture 存成含樣式的完整頁面，在真實 Chrome 跑（與現有 Chrome 測試同一類，需環境變數）。
- 〔第 1 輪改，W3〕**上限**：區塊數 2,000、全部文字（含標籤）UTF-8 合計 256 KiB（常數定在 contracts）。超過時只送前面放得下的完整區塊並標 `truncated: true`，匯入頁持續顯示「內容不完整」。schema 擋超量請求，service worker 不轉送，所以不會碰到 1 MiB 的協定斷線。
- 新增 content script 白名單操作 `submit_resume_capture`（相加）：`{platform, url, capturedAt, truncated, nameText, blocks: [{kind, level, label, text, continues}]}`；`kind` 是封閉列舉；`level` 只有標題與清單項有（1–6），其他種類是 null；〔第 2 輪補，W6〕`nameText` 是登記的姓名元素的文字（沒登記或找不到是 null，可以在根節點外），只給 helper 在本機遮蔽與預填，不送模型。〔第 1 輪補，N5〕區塊不帶編號，編號由 helper 依順序配發（b1、b2…），頁面字串不會變成提示的結構。成功只回 `{ok: true}`。
- 〔第 1 輪改，W2〕**發送者驗證按「操作×頁型」**：`submit_job_capture`、`submit_message_capture` 維持現行（只在職缺頁規則通過時）；`submit_resume_capture` 只在該站履歷頁規則通過時；兩種規則互不放行。都要主框架、平台與發送頁相符。〔N4〕履歷擷取的 `url` 只存 origin＋路徑（不存查詢字串與 #），而且必須等於發送頁網址的 origin＋路徑，不符就拒。網址只存本機、不送模型。
- 照片：本規格**不**從網頁抓照片（需要另外取圖、可能帶 cookie）；照片由使用者在 RoleCraft 自己選本機檔（5.4）。

### 5.2 helper：匯入工作階段

- 收到 `submit_resume_capture` 後建立一個匯入工作階段，來源標「網頁：<平台>」，不自動呼叫模型。
- 〔第 1 輪改，W5；擁有者 2026-10-12 裁決，Q11＝A〕**保存**：與 PDF 匯入相同——只在 helper 記憶體（與 PDF 共用最多 20 筆、超過丟最舊），不寫入資料區；helper 重開就消失，使用者在履歷頁再點一次圖示（或按快捷鍵）即可。
- 〔第 1 輪改，W4〕**契約（相加，PDF 既有形狀不變）**：網頁來源的原文是區塊清單（helper 配發的編號、種類、層級、標籤、文字，以及是否截斷），欄位出處是區塊編號；不得把區塊轉成假的頁碼／行號。`import.get`、`import.ai_status` 的回應要能分辨兩種來源，預覽依來源顯示「第 N 頁第 M 行」或「區塊 bN」。模型輸出的來源編號依來源種類驗證（PDF `頁-行`、網頁 `b<數字>`），格式不對整份不合格。上限內最大的擷取，對應的 `import.get` 回應要低於 1 MiB（以測試證明）。〔第 2 輪補，W3〕模型可以重複照抄同一個來源，所以草稿大小另外限制：通過檢查的 AI 草稿序列化後 UTF-8 超過 512 KiB 就整份判失敗（輸出不合格）、不回傳草稿（PDF 與網頁共用），`import.ai_status` 的回應因此一定低於 1 MiB。
- 〔第 1 輪改，Q3 協調者決定〕**編輯器取得擷取**：新增（相加）`import.latest_capture`，回最近一次網頁擷取的 importId、平台、擷取時間、是否截斷，沒有就 null。匯入頁顯示它，使用者按「使用這份」才進入核對（`import.get`）；擷取送達本身不改變編輯器正在核對的內容。〔裁決後補〕擷取成功後 service worker 開的編輯器分頁（5.1）也是這樣顯示。
- 〔第 1 輪補，W14〕**手動輸入**：新增（相加）`import.start_manual`，建立沒有原文的匯入工作階段，讓使用者直接填表確認（D18 的手動路線）。匯入頁一律提供「手動輸入」入口；網址不支援、擷取失敗、AI 不可用、LinkedIn（D5）都走這裡。
- 〔第 1 輪補，W9；擁有者 2026-10-12 裁決，Q8＝A〕**確認寫入**：`import.confirm`（網頁、PDF、手動共用）在資料區已有一份 Profile 時更新那一份（保留 id），沒有才新增；已有多份（舊資料）時不寫入並提示。確認前畫面明示「會取代目前的個人資料」。舊的客製履歷段落用公司＋職稱＋起始日期對經歷（contracts `SectionPlacement`），對不到的照現行規則不能匯出。

### 5.3 AI 整理與檢查（沿用 P1-T069，來源單位換成區塊）

- 〔第 1 輪改，W6〕**去個資**（送模型前，在本機）：
  - 區塊依順序當成行，套用 P1-T069 同一套規則；標籤＋值區塊以「標籤：值」判斷，標籤是個資標籤就整塊移除、值由本機預填。〔第 2 輪補，W18〕標 `continues` 的同標籤區塊是同一欄位的續行：一併移除，值接回同一列（預填與遮蔽都用接回後的完整值，不適用「同一標籤只留第一個」）。
  - 聯絡區：「聯絡方式」等標題下的區塊，移除到下一個同級或更高級的標題為止。
  - 〔第 2 輪改，W6〕**已知姓名**：(1) 該站在 registry 與根節點一起登記的姓名元素（以樣本驗證；沒登記或找不到就視為沒有）的文字，套 P1-T069 頁首姓名同一個切法（`cleanHeaderName`）；(2) 標籤為姓名的區塊值；(3) 資料區既有 Profile 的姓名；(4) 使用者在匯入頁填的姓名（可填多個寫法，例如中文名與英文名；只用於本機遮蔽與預填，`import.ai_parse` 相加選填）。既有 Profile 的聯絡資料值也加入遮蔽。
  - **別名**：任何區塊以已知的中文姓名開頭、後面接 1–3 個大寫開頭的英文字時，那段英文也當姓名遮蔽（P1-T069 `headerNameAlias` 同一規則）。
  - **送出條件**：(1) 或 (2) 至少一個成立，才算辨識出本次頁面的姓名；否則要使用者在匯入頁確認姓名（預填 (3)，可修改、可加寫法）後才送。只有舊 Profile 的姓名不算本次頁面的姓名已辨識——網頁常把姓名放在沒有標籤的大標題，寫法也可能和舊資料不同。
  - email、電話、身分證字號的通用遮蔽照舊。
- 提示中的每個區塊帶種類、層級與標籤（例如「[b12 h3] 銷售業務」「[b13 標籤=職務類別] 內勤業務」），整份放在隨機界線的資料區塊內（plan D6）。
- 〔第 1 輪改，W8〕**照抄檢查以區塊為來源單位**（每個區塊只有一行，見 5.1 第 3 點，`match.ts` 的行規則可以直接套）：值必須出自引用的區塊；描述以換行分段，每段等於一個或連續幾個引用區塊的全文，依序用完所有引用區塊（可略過沒引用的區塊）；標籤不算來源文字。〔第 2 輪改，W8〕「至今」類字眼獨占一個區塊時：結束日期的引用只能是這個區塊；程式另外往前找日期上下文——略過只有區間分隔符（~ - – — 至 to）的區塊，遇到的第一個區塊去掉結尾的區間分隔符後，必須**整個**是年份或年月（`isDateValue`），而且兩者之間沒有標題區塊，才算仍在職（「2020 年得獎作品」不算）。上下文區塊不列入引用、不受「每個引用都要用到」約束。其他日期、詞界規則沿用 `match.ts`。
- 〔第 1 輪補，W7〕欄位值在還原佔位字時還原出姓名或個資，畫面在該欄標示「含姓名或聯絡資料」，提醒使用者確認前刪掉。〔擁有者 2026-10-12 裁決，Q9＝A〕「不送模型」只管匯入整理：確認後存進經歷描述的文字，之後產生履歷、自介照現行規則送出。
- 〔第 1 輪改，W15；擁有者 2026-10-12 裁決，Q4＝B〕**何時呼叫模型**：網頁來源一律按鈕。使用者在匯入頁開啟某份擷取（「使用這份」）、核對區塊與截斷標示後，按「用 AI 整理」才呼叫模型；擷取送達、`import.latest_capture` 查詢、開啟或切換工作階段都不會觸發（`useAiParse` 的自動開始對網頁來源一律關閉）。本次頁面的姓名沒辨識出來時，要先確認姓名（見上方「送出條件」）才能送。失敗或不可用時，畫面顯示擷取到的區塊供手動輸入。PDF 匯入維持現行（104 版面按鈕、其他格式自動開始），不在本規格改。

### 5.4 照片與 PDF 輸出

〔第 1 輪改，W10、W11、W12；Q6 協調者決定〕

- **存放**：資料區只存一張「目前的照片」，獨立於 Profile（Profile schema 不變、不進 `ProfileInput`；匯入、AI 重整、確認都不碰照片）。存在資料庫，不放進檔案儲存區（避免被孤兒清掃刪掉）。
- **加入**：新增（相加）`photo.pick`：helper 開系統選取器（只限 JPEG／PNG、10 MB 以下），解碼後重新編碼成 JPEG、最長邊縮到 1,200 px，〔N1〕並去掉所有中繼資料（EXIF，含 GPS 位置與拍攝裝置）；解不開就拒絕。使用者在選取器選定、處理成功即生效，不等匯入確認。請求沒有路徑；回應只有照片資訊（格式、尺寸、雜湊）與縮圖。
- 〔第 2 輪補，W19〕`photo.pick` 列入選取器操作（contracts `BRIDGE_PICKER_OPERATIONS`，用選取器的長逾時）；解碼與重新編碼必須在選取器的處理餘裕內完成，超過就放棄、不寫入。客戶端逾時不會取消 helper 的工作，所以 `photo.*` 失敗或逾時後，編輯器一律重新讀 `photo.get`，以實際狀態顯示。
- **查詢與刪除**：`photo.get`（目前照片資訊＋縮圖，回應低於 1 MiB）、`photo.remove`。
- **匯出**：`ResumeDocument` 相加選填照片（data URI），模板在頁首放照片；沒有照片時版面照常。〔第 2 輪改，W12〕匯出版本相加記錄照片 ID 與雜湊（R3）。照片不送模型、不出現在任何提示。
- **刪除與更換**：照片印進匯出 PDF 後就是「素材」（匯出版本保存了它的副本），刪除照片套 D19：含這張照片、未投遞的匯出版本整份刪除，已投遞的保留並明示；確認前畫面先說明。〔第 2 輪補，W12〕素材身分是照片 ID：每次加入（含更換）都由 helper 配發新的照片 ID，刪除時以照片 ID 記入已刪素材；不用雜湊當身分（刪掉後再選同一張照片，處理結果雜湊相同，新的匯出不能因此被擋）。〔擁有者 2026-10-12 裁決〕更換視同刪除舊照片（套 D19）：更換＝刪除舊照片＋加入新照片，在同一個交易完成；已有照片時，畫面先說明、使用者確認後才開選取器，取消選取不變動。

## 8. 驗收

- 擴充功能：每個上線網站的履歷頁有去識別化 DOM 樣本 fixture（含樣式的完整頁面）與預期區塊，在真實 Chrome 比對（N6）；〔第 1 輪補，W1〕區塊抽取規則另以合成 DOM 測試（巢狀清單、`li` 內含 `p`、隱藏元素、表格、標籤＋值、表單控制項、`br` 換行與 `continues`、找不到根節點；〔第 2 輪補，N5〕七層清單最內層記 6）。網址規則、白名單操作有測試；〔W2〕操作與頁型錯配、`url` 與發送頁不符、非主框架、平台不符被拒。
- 〔擁有者 2026-10-12 裁決，D9〕觸發：點圖示時，履歷頁網址 → 注入履歷頁擷取腳本；職缺頁、不支援的網站、拿不到分頁或網址 → 開編輯器、不注入。快捷鍵：履歷頁、職缺頁各自注入對應的腳本，都不符只在圖示提示、不注入。registry 裡同一站的職缺頁與履歷頁規則不重疊。manifest 權限仍只有 `activeTab`、`scripting`、`nativeMessaging`、沒有 popup（現行 manifest 測試照舊通過）。履歷擷取成功後開一個編輯器分頁；找不到根節點時不送、不開編輯器、頁面顯示提示；送出失敗、注入失敗都不開編輯器。
- 〔第 1 輪補，W3〕上限：超過上限時只送完整區塊並標截斷；上限內最大的請求與對應的 `import.get` 回應都低於 1 MiB；〔第 2 輪補〕模型重複照抄同一個大區塊、草稿超過 512 KiB 時整份判失敗。
- 去個資：送給模型的提示字串測試中不含姓名、電話、email、地址、照片；〔W6〕包含「姓名只出現在沒有標籤的標題」的案例；〔第 2 輪補〕「林測試 Alex Lin」的英文別名被遮蔽；本次頁面的姓名沒辨識出來、使用者也沒確認時不送；〔W18〕分成多行的地址，預填與遮蔽都是完整值。
- 〔擁有者 2026-10-12 裁決，Q4＝B〕網頁來源：擷取送達、`import.latest_capture` 查詢、開啟或切換工作階段都不送 `import.ai_parse`；按「用 AI 整理」才送。
- 照抄檢查：以區塊為來源的捏造案例被丟棄（沿用 P1-T069 測試類型）；〔W8〕被切開的多行描述、「2019/03」「~」「至今」三個區塊等真實原文被接受；〔第 2 輪補〕「2020 年得獎作品」後接「至今」、中間隔標題的「至今」被丟棄。
- 〔第 1 輪補，W9〕再次匯入並確認後，資料區仍只有一份 Profile。
- 照片：選取、更換、刪除；〔N1〕存下的照片沒有 EXIF 等中繼資料；〔W12〕刪除與更換照 D19 處理含照的匯出版本；〔第 2 輪補〕刪掉後再選同一張照片，新的匯出不被擋；〔W19〕選取超過一般逾時仍能完成，失敗或逾時後畫面顯示的是 `photo.get` 讀回的實際狀態；匯出含照片／不含照片兩種版面，〔W17〕含照版要目視確認照片有印出、沒有遮住文字；照片不出現在任何提示。
- 複製按鈕：〔W13〕個人資料各欄複製的內容等於 helper 讀回的已確認值，〔W20〕與畫面不一致時不複製、先更新畫面；客製段落有任何 R1 問題、在 blockers 裡（含只逐段確認、未接受）或有未儲存修改時不能複製。
