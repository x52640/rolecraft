### D9（點圖示擷取）：權限查證

結論：**不需要任何新權限**，manifest 維持 `activeTab`、`scripting`、`nativeMessaging`。

- 現行 manifest 已有 `activeTab`、`scripting`（`apps/extension/src/manifest.ts` 的 `PERMISSIONS`；`manifest.test.ts` 鎖住只有這三個、沒有 host 權限、工具列沒有 popup）。
- Chrome 官方 activeTab 說明（developer.chrome.com 的 activeTab 概念頁，2026-10-12 讀）：「Executing an action」（點工具列圖示）和「Executing a keyboard shortcut from the commands API」都會授予 activeTab；授予期間可以對該分頁 `scripting.executeScript`（要另外宣告 `scripting`），也能從回傳 `tabs.Tab` 的 API 拿到網址；離開該網站或關分頁就收回。官方 Focus Mode 範例就是只宣告 `activeTab`＋`scripting`，在 `action.onClicked` 裡讀 `tab.url` 再對分頁注入。
- 現行快捷鍵路徑（`background/main.ts` 的 `chrome.commands.onCommand` → `actions.ts` 的 `triggerCapture`）本來就是靠 activeTab 拿分頁網址、再注入；點圖示是同一種授權，`chrome.action.onClicked` 也會收到分頁物件。
- 現行點圖示本來就會授予 activeTab（授予與處理函式做什麼無關），只是處理函式沒拿來用。所以授權範圍不變，只是改成在履歷頁拿來注入。
- 不採用（都要新權限或改按鈕行為）：依頁面變換圖示或提示文字（`tabs` 或 `declarativeContent`）、右鍵選單（`contextMenus`）、popup（改變其他頁面的按鈕行為，manifest 測試也鎖住沒有 popup）。

### D9：協調者補的細節與理由

| 細節 | 理由 |
|---|---|
| 擷取成功（helper 回成功）後 service worker 開一個編輯器分頁，預設就是匯入頁，顯示 `import.latest_capture`；仍要按「使用這份」，也不呼叫模型。圖示與快捷鍵觸發一樣 | 派工單的保守做法。點了圖示要看得到結果；在 helper 回成功之後才開，編輯器查到的一定是剛送達的這份，不會先顯示舊擷取。編輯器預設頁本來就是匯入頁（editor `app/routes.ts` 的 `DEFAULT_ROUTE_PATH`），不必加路由 |
| 找不到本文根節點、送出失敗、注入失敗都不開編輯器，只提示（頁面右上角或圖示徽章） | 找不到根節點時 content script 什麼都不送，service worker 不知道失敗；若改成「一律先開編輯器」，匯入頁可能顯示上一次的擷取而被誤用。要失敗也開編輯器，得加 content script 回報結果的新管道，超出保守做法 |
| 失敗提示寫明「沒有擷取或送出任何內容」，並指向「手動輸入」與「在其他分頁點圖示開啟編輯器」 | 在履歷頁上點圖示不會開編輯器，提示要告訴使用者怎麼走下一步 |
| 職缺頁點圖示照舊開編輯器；職缺擷取仍只用快捷鍵 | 裁決原文「其他頁面照舊開編輯器」 |
| 職缺頁、履歷頁的擷取腳本分開兩支，由 service worker 依網址選 | 頁型只在一個地方判斷；發送者驗證本來就按「操作×頁型」（W2） |
| 履歷頁網址規則要窄到只符合要讀的那一種頁（併入 Q2） | 符合的頁面點圖示就不再開編輯器；規則太寬，104 其他頁面也會變成擷取 |
| 圖示提示文字、擴充功能說明、快捷鍵說明改成講清楚兩種行為 | 現行圖示提示是「開啟 RoleCraft 編輯器」，改了行為不改字會誤導 |

代價（已寫進 5.1）：在履歷頁上點圖示不再開編輯器；擷取失敗時要到其他分頁點圖示才能開編輯器；每點一次就是一次新擷取，成功就多一個編輯器分頁。
